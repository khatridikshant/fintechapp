Complete Architecture Specification
I would make this the project's canonical architecture document — something a human developer or an AI coding agent can read and understand.

1. Product definition
The product is an offline-first desktop business management application for individuals and small businesses.

It combines:

Accounting

Expense tracking

Income tracking

Invoicing/billing

Customer management

Supplier management

Product management

Inventory/stock management

Purchases

Payments

Financial reporting

Cloud backup/synchronization

The application is primarily operated on the user's computer.

The user's accounting/business database lives locally in SQLite. The active fiscal year has its own SQLite database. A new SQLite database is created for each fiscal year; a fiscal-year database is never allowed to grow across multiple fiscal years.

Internet connectivity is not required for normal business operations.

When internet connectivity is available, the active fiscal-year database can be synchronized/backed up to the cloud. Normal business operations do not require internet connectivity, but concluding a fiscal year is an explicitly online operation because the completed fiscal-year SQLite database must be archived on the server before the transition is finalized.

2. Fundamental architecture principle
There is one extremely important rule:

The local application is the primary business system. The cloud is primarily responsible for identity, synchronization, backup, and recovery.

Therefore:

LOCAL COMPUTER
     │
     ├── Business operations
     ├── Accounting
     ├── Inventory
     ├── Billing
     ├── Reports
     └── SQLite
          │
          │ Sync / Backup
          ▼
CLOUD
     │
     ├── User account
     ├── Authentication
     ├── Backup metadata
     ├── Database snapshots
     └── Restore

The user should be able to continue working when:

Internet = OFF

9. Accounting model
The accounting engine uses double-entry accounting.

Every financial transaction must satisfy:

TOTAL DEBITS = TOTAL CREDITS

A journal entry contains:

JournalEntry
    id
    date
    description
    reference
    lines[]

Each line:

JournalLine
    account_id
    debit
    credit

Example:

Expense: Rs 500
paid from Bank

becomes:

Journal Entry

Dr Office Expense       500
Cr Bank                 500

21. Database philosophy
SQLite is the source of truth for the local book and active fiscal year. The currently active fiscal-year SQLite database is the authoritative local working database. Historical fiscal-year databases are immutable archives and are not used for current-period transactions.

Constraints

Transactions

Don't rely on the application code alone to maintain data integrity.

26. Fiscal-year database architecture
The application shall use one SQLite database per fiscal year.

The active book therefore has a database lifecycle like:

FY 2081/82 SQLite
        ↓
Conclude fiscal year
        ↓
Archive completed SQLite on server
        ↓
Create FY 2082/83 SQLite
        ↓
FY 2082/83 becomes active

The fiscal-year database is the working source of truth for that fiscal year. The application shall not keep one SQLite database growing indefinitely across multiple fiscal years.

Example:

Book ABC
│
├── accounting-FY-2081-82.db   ← historical/read-only
├── accounting-FY-2082-83.db   ← historical/read-only after close
└── accounting-FY-2083-84.db   ← current active database

Only the current fiscal-year database is writable during normal operation.

Completed fiscal-year databases shall become immutable from the application's normal business workflow. Historical years may be opened or downloaded for reporting and review, but they shall be opened in read-only mode.

27. Fiscal year definition
The default fiscal year for a Nepal-focused deployment shall be:

1 Shrawan → end of Ashadh

Fiscal years shall have explicit identifiers such as:

FY 2082/83

Every transaction shall belong to a fiscal year through its transaction date and active database. The application shall validate that a transaction date belongs to the currently active fiscal year before posting it.

A closed fiscal year shall reject new financial transactions unless an explicit controlled period-reopen workflow is implemented.

The fiscal-year transition shall carry forward the balances and opening information required by the accounting model. Revenue and expense activity from the completed year shall not simply be copied into the new database as new transactions.

28. Fiscal year conclusion
Concluding a fiscal year is a controlled business operation and requires an internet connection.

Normal business operations remain offline-first, but fiscal-year conclusion is an exception because the completed SQLite database must be successfully archived on the server before the transition is finalized.

The process shall be:

1. User selects "Conclude Fiscal Year".
2. Application verifies that internet connectivity is available.
3. Application validates the active SQLite database.
4. Application checks for invalid or unbalanced journals, incomplete required transactions, and other blocking conditions.
5. Application calculates the year-end accounting state.
6. Application creates required closing entries.
7. Application determines the opening balances required for the next fiscal year.
8. Application creates a consistent final snapshot of the completed fiscal-year SQLite database.
9. Application calculates the SHA-256 checksum and validates SQLite integrity.
10. Application uploads the completed SQLite file to server-side object/file storage.
11. Server verifies ownership, fiscal year, checksum, file size, and archive metadata.
12. Server confirms that the fiscal-year archive has been successfully stored.
13. Only after server confirmation may the local application create and activate the next fiscal-year SQLite database.
14. The new SQLite database is initialized with the required opening balances and other explicitly carried-forward data.
15. The new database is validated.
16. The previous fiscal year is marked closed and the new fiscal year becomes active.

The application shall never delete or discard the previous fiscal-year database before the server has confirmed successful archival.

If internet connectivity is unavailable, the user may continue normal operations in the current fiscal year, but the fiscal year cannot be concluded.

If the archive upload fails, the current fiscal-year database remains active and writable. The application shall not partially complete the year transition.

If creation or initialization of the new fiscal-year database fails after the server archive has succeeded, the application shall preserve the archived old year and retain a safe local recovery copy of the old database until the transition has been successfully completed.

29. Carry-forward rules
At fiscal-year conclusion, the application shall carry forward the balances required to establish the opening state of the next fiscal year.

Typical carried-forward balances include:

Cash
Bank
Accounts Receivable
Accounts Payable
Inventory
Fixed Assets
Loans and other liabilities
Owner's Equity / retained earnings as applicable
Other balance-sheet accounts requiring opening balances

The application shall not copy the completed year's ordinary sales, purchases, expenses, payments, or journal history into the new fiscal-year database merely to preserve history. Those records remain in the archived database for the completed fiscal year.

Revenue and expense accounts shall be reset for the new fiscal year according to the accounting model, with the completed year's result transferred through the appropriate equity/retained-earnings treatment.

Inventory shall carry forward the required opening quantity and valuation. Historical inventory movements remain in the completed fiscal-year database.

The exact inventory valuation method shall be explicitly selected and documented before implementation. The application shall not silently choose FIFO, weighted average, moving average, or another costing method.

Negative inventory behavior shall also be explicitly defined before implementation.

30. Fiscal-year database naming and metadata
Each SQLite file shall be identifiable by book and fiscal year.

Example:

book-id: BOOK-001
fiscal year: FY 2082/83
local file:
accounting-FY-2082-83.db

The database metadata shall identify at least:

book_id
fiscal_year_id
fiscal_year_start
fiscal_year_end
database_schema_version
created_at
last_modified_at
status

The fiscal-year identifier must be validated against the application configuration and cloud metadata. A database from one book or fiscal year must not be silently opened as another book or fiscal year.

31. Historical fiscal-year access
Completed fiscal-year databases shall remain available as historical records.

When a user needs an old year, the application may:

1. Download the archived SQLite file from the server.
2. Verify ownership and authorization.
3. Verify the checksum.
4. Run SQLite integrity checks.
5. Validate the fiscal-year metadata.
6. Open the database in read-only mode.

Historical databases shall not be used for normal posting of new transactions.

If a correction to a closed fiscal year is ever required, the application shall use an explicit controlled period-reopen or adjustment workflow. It shall never silently modify an archived database.

32. Book and business lifecycle
V1 shall support one book per account.

A book represents one business/accounting environment.

The application shall support the following lifecycle operations where applicable:

Create book
Open book
Rename book
Archive book
Conclude fiscal year
Reopen a closed period through an explicit controlled workflow

Archiving a book shall make it read-only. Deletion, if implemented, shall require an explicit warning and shall not be treated as a normal accounting correction mechanism.

Multiple active books per account are outside the V1 scope unless explicitly added later.

33. Currency
Each book shall have one base currency in V1.

The default currency for the Nepal-focused deployment shall be:

NPR / Rs.

The user may change the displayed currency setting where supported, but changing the base currency after financial transactions exist shall be restricted and shall require an explicit controlled process.

Multi-currency accounting is outside V1 unless separately specified.

Financial calculations shall use fixed decimal/decimal-safe representations and consistent rounding rules. Binary floating-point values shall not be used for authoritative financial calculations.

34. Authentication and sessions
The desktop application shall support:

Login
Logout
Authenticated session handling

The initial session policy shall use a seven-day session validity period.

When the session expires, the application shall log the user out and require authentication again.

Password reset and email verification are outside V1 unless separately specified.

Authentication state shall remain separate from accounting data and shall not be restored from an old SQLite backup.

35. Invoice numbering and Nepal business-document requirements
For the Nepal-focused deployment, finalized invoice numbering shall be sequential within the applicable fiscal year and document type.

The sequence shall start at 1 for each fiscal year where that numbering policy applies.

A finalized invoice number shall never be reused or duplicated.

Draft invoices may be edited or deleted before final issuance. A draft should not consume a finalized invoice serial until the invoice is actually issued.

Once issued, an invoice shall not be physically deleted through normal business operations. Corrections shall use appropriate corrective documents such as credit notes, debit notes, sales returns, payment reversals, or other explicitly defined correction workflows.

Credit notes and debit notes shall have their own controlled sequences where required, shall reference the original invoice, and shall preserve an audit trail.

The final document number shall be determined from the fiscal year, issue date, document type, and configured numbering policy.

Business profile information shall support the information required for Nepal operations, including PAN and VAT-related information where applicable.

Tax behavior shall be configurable and rule-based rather than hardcoded throughout the accounting engine. The model shall support, where applicable:

VAT registered / not registered
PAN information
Taxable transactions
Zero-rated transactions
Exempt transactions
Tax-inclusive pricing
Tax-exclusive pricing
Separate tax amount
Tax rule/version information

Nepal's applicable tax rules shall be verified against current authoritative requirements before production release and shall not be treated as permanently fixed application constants.

36. Deletion, reversal, and correction policy
Draft and unposted records may be deleted where appropriate.

Finalized financial transactions shall not normally be physically deleted.

Corrections shall preserve the original transaction and use an appropriate compensating operation, such as:

Reversal
Credit note
Debit note
Payment reversal
Purchase return
Sales return
Inventory adjustment

A reversal shall create the opposite accounting effect while preserving the original journal and audit trail.

Inventory movements shall not be physically deleted from normal operations. Corrections shall use compensating inventory movements with references to the original movement.

Every corrective transaction shall remain traceable to the original business event.

37. Cloud synchronization
The cloud stores versions of the active fiscal-year SQLite database. Completed fiscal-year databases are archived as immutable SQLite files.

Each active-year revision has metadata:

revision
book_id
fiscal_year_id
file_path or object_key
file_size
checksum
created_at
database_version
status

The actual SQLite file is stored in object/file storage. PostgreSQL stores only the metadata and storage reference required to locate and validate that file.

Cloud synchronization is an online feature. It is not required for normal local accounting operations. Fiscal-year conclusion is a separate controlled online operation and cannot be finalized until the completed SQLite file has been successfully archived on the server.

38. V1 synchronization restriction
To keep synchronization manageable:

One book should have one active desktop installation in V1. The active installation operates on one current fiscal-year SQLite database at a time.

This eliminates a huge amount of complexity.

You don't need to solve:

Laptop A changed invoice
Laptop B changed invoice

simultaneously.

Later, multi-device synchronization can be designed separately.

39. Sync process
For the active fiscal year:

Desktop:

Active SQLite
 ↓
Validate
 ↓
Create consistent snapshot
 ↓
Calculate SHA-256
 ↓
Upload

Server:

Authenticate
 ↓
Verify book ownership
 ↓
Verify fiscal year
 ↓
Verify expected revision
 ↓
Store SQLite file in object/file storage
 ↓
Create/update PostgreSQL metadata
 ↓
Return new revision

The server shall never treat an unverified upload as a valid backup. The checksum, file size, book, fiscal year, and database/schema version shall be validated before the backup is marked successful.

40. Restore process
Never immediately overwrite the current database.

For an active fiscal-year restore:

Current DB
   ↓
Local emergency backup
   ↓
Authenticate user
   ↓
Verify authorization/license
   ↓
Download cloud snapshot
   ↓
Validate metadata and checksum
   ↓
Run SQLite integrity checks
   ↓
Run required migrations if applicable
   ↓
Replace current DB
   ↓
Open application

For a historical fiscal-year database, the same verification process applies, but the resulting database shall be opened read-only.

If the local database is lost and no valid cloud snapshot or fiscal-year archive exists, the application cannot recover the missing data.

Restoring an accounting database shall never restore obsolete license, authentication, subscription, or device-authorization state.

The desktop framework should remain replaceable. AI-assisted development does not depend on one UI toolkit being the core of the application; the critical requirement is that accounting rules, data integrity, and fiscal-year lifecycle remain isolated from the presentation layer.



Desktop security requirements

The desktop application is a financial-data application and must be designed with a least-privilege security model regardless of the selected UI framework.

The following are non-negotiable architectural requirements:

No UI component may directly access SQLite.
No UI component may directly execute arbitrary SQL.
No UI component may directly access operating-system secrets or unrestricted filesystem operations unless explicitly required by a bounded application service.
Privileged operations shall be exposed through typed application services or commands.
Input crossing process or module boundaries shall be validated.
Remote content shall not be trusted as executable application code.
Dependencies shall be monitored and updated through a controlled process.
Release artifacts shall be signed where the selected platform supports application signing.
Sensitive local credentials, license state, and tokens shall use protected operating-system storage where available.
Backups and cloud transfers shall use authenticated and encrypted channels.

The exact security controls may differ by desktop framework, but the separation between presentation code and privileged business/data operations shall remain mandatory.

Licensing, Authentication, and Offline License Enforcement

The application shall use a server-controlled licensing system for user authentication, subscription status, and license authorization. The Laravel backend shall be the authoritative source for user accounts, licenses, subscriptions, books, and registered desktop installations. The desktop application shall authenticate the user with the backend when an account session is established and shall obtain a cryptographically signed license authorization that allows the application to operate.

After successful authentication and license verification, the desktop application shall be capable of operating normally without an active internet connection. Normal accounting, invoicing, billing, inventory, customer, supplier, reporting, and other business operations shall not require continuous internet connectivity. Internet connectivity shall primarily be required for authentication, periodic license validation, cloud synchronization, backup, restore, fiscal-year conclusion/archival, and other explicitly online features.

The backend shall issue a signed license authorization containing the information required by the desktop application to determine whether the user is authorized to operate the application. The authorization should contain, at minimum, the license identifier, user identifier, book identifier, license status, license expiration date, issuance date, next required server validation time, and license revision. Where device binding is enabled, the authorization may also contain the registered device identifier. The backend shall sign this authorization using a private signing key.

The desktop application shall contain only the corresponding public verification key and shall verify the cryptographic signature of every license authorization before trusting it. The desktop application shall never trust an unsigned or locally modified license file. The private signing key shall never be included in the desktop application or distributed to clients. This ensures that the desktop application can verify that a license authorization was genuinely issued by the backend without requiring an internet connection for every verification.

The system shall distinguish between the actual license expiration date and the next required online validation date. The license expiration date represents the end of the user's authorization to use the application and shall be enforceable locally. The next validation date represents when the application should contact the backend again to confirm the current license, subscription, device, or account status. These two values shall not be treated as the same concept.

When the application has internet connectivity and the next validation time has been reached, the application shall contact the backend and request a fresh license authorization. The backend shall verify the user's account, license, subscription status, registered book, and registered desktop installation before issuing a new authorization. If the validation succeeds, the application shall securely store the new signed authorization and continue operating normally.

If the application is offline when periodic validation is due, the application shall continue operating according to the configured offline-validation policy. The system should provide a defined offline grace period for periodic server revalidation so that a temporary loss of internet connectivity does not unnecessarily prevent normal business operations. However, the actual license expiration date shall remain an absolute local enforcement boundary unless the licensing policy explicitly defines otherwise.

The desktop application shall be able to determine that a license has expired without contacting the backend. If the current date reaches or passes the locally verified license expiration date, the application shall no longer allow normal business operations. The application shall lock the application or terminate the authenticated session and require the user to obtain a valid license authorization before business operations can resume. Internet connectivity shall not be required merely to determine that an already-issued license has expired.

License enforcement shall not delete, corrupt, or modify the user's accounting data. When a license expires, the application shall protect the business data and prevent unauthorized business operations while preserving the local SQLite database and all existing records. Re-authentication or renewal of the license shall restore access to the existing business data when the account is authorized again.

The license and authentication state shall be maintained separately from the accounting database and shall not depend on restoring an old accounting SQLite snapshot. Restoring a business database shall therefore never restore an older license state, subscription state, authentication state, or device authorization. License information shall be stored in an appropriate protected application storage mechanism separate from normal accounting data.

The application shall implement reasonable protection against local clock manipulation. It shall record trusted server time obtained during successful online validation and may compare subsequent local timestamps against the last trusted time to detect significant clock rollback. The application may also maintain additional integrity information required to identify suspicious changes to local licensing state. These mechanisms are intended to provide practical license enforcement and tamper detection; they shall not be treated as an absolute guarantee against a user with full control over the client machine.

The licensing system shall support the application's V1 restriction of one book and one active desktop installation per account where applicable. The backend may maintain registered desktop installation or device information and shall be responsible for determining whether a new installation is authorized. Device registration, license validation, subscription status, and account authorization shall remain backend responsibilities and shall not be implemented as accounting-domain logic.

The licensing implementation shall be isolated from the accounting, inventory, invoicing, purchasing, sales, and reporting domains. A dedicated security/licensing component shall manage authentication sessions, license authorization, signature verification, device identity, secure local storage, license expiration, periodic validation, trusted server time, and clock-integrity checks. Financial business operations shall not contain licensing logic.

The application shall fail safely when licensing information is missing, invalid, corrupted, expired, or fails cryptographic verification. Invalid or tampered license information shall never grant access to protected business operations. At the same time, licensing failures shall not result in deletion or modification of the user's accounting records.

The licensing system shall be covered by automated tests. Tests shall verify successful license verification, invalid signatures, expired licenses, future licenses, periodic validation, offline operation, offline expiration, clock rollback detection, corrupted local license state, device authorization, renewal after expiration, and restoration of accounting data without restoring obsolete licensing state. Licensing behavior shall be deterministic and independently testable without requiring the accounting domain to communicate directly with the licensing backend.
